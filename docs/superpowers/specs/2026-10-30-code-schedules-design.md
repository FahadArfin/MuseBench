## Intent and approach

Use the existing Code Scheduled destination, owned native runtime contexts and SQLite profile. Each occurrence creates a fresh Code chat in the chosen project without changing the visible chat or its draft. A local timer is simpler and matches the app-open requirement. OS scheduled jobs would require separate process ownership and unattended authentication; hosted scheduling requires an external service. Neither is part of this feature. These implementation choices are the builder's calls within the approved roadmap.

## Behavior

- A compact list shows enabled/paused schedules, next run, remaining attempts and recent outcome. An editor captures name, prompt, project, first time, optional fixed interval, maximum total attempts and existing model/reasoning/approval/budget choices. A separate review and **Enable schedule** action explicitly authorizes future runs and states that they consume Muse usage. Save/edit always leaves a schedule paused. Full access is an explicit, default-off choice; approved workspace tools remain off for scheduled connections.
- Start time is entered in the computer's local time and stored as an absolute instant. Repeat intervals are elapsed time, clearly labeled **Every … minutes/hours/days**, not calendar-day rules. One-off and 15-minute through 30-day intervals are supported. At most 50 schedules, 100 total attempts per schedule, a 16,000-character prompt and existing standard/extended/deep runtime budgets. Missing model means the native default, never an invented fallback.
- The timer runs every 15 seconds while MuseBench is open. Due occurrences more than 60 seconds late are recorded as skipped and advance directly to a future occurrence; there is no catch-up burst. Busy/overlapping checkout work is skipped. Claim and next-time advancement are persisted before admission. Attempts count admission attempts, including failures, not just successful replies. Successful owned, confirmed completion is the only success state.
- Pause prevents future occurrences without stopping a current run. Stop targets the exact schedule occurrence and pauses future work. Any pending approval/question, failed/uncertain outcome, missing project, changed canonical root or failed admission pauses future runs. An interrupted active occurrence becomes uncertain on restart and is never replayed. Only future authorized occurrences survive ordinary restart. Editing/removal while active is rejected. Run history links to the owning chat, including after restart; deletion of a schedule retains its chats.
- Scheduled text is sent through the same native context, filesystem, permission, budget, run receipt, source capture and cancellation paths as manual Code work. The selected workspace/chat/draft remains untouched. Running scheduled work participates in update blockers and existing Work activity. Shutdown stops timers, prevents new admission and preserves uncertain outcomes.
- Browser preview uses the same controls with clearly labeled in-memory samples; it never runs a provider or pretends a scheduled model run succeeded. Both real-controller tests and shared browser/Electron tests use injected runtimes only.

## Acceptance and boundaries

Verify time advancement, stale revisions, explicit enablement, bounded attempts, durable claim before send, crash recovery, no overlap, no catch-up, question/approval pause, exact stop ownership, selected chat/draft preservation, IPC rejection of internal flags, missing/changed projects and shutdown races. Review the UI at narrow width and with keyboard access. Preserve the current release policy and all checks. Published/installed proof is separate from injected provider tests. Real scheduled inference remains an external acceptance prerequisite requiring an explicitly authorized schedule or new bounded model-test authorization.
