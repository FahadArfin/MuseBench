# MuseBench validation

Date: 25 October 2026. Local Windows build; no deployment or publication.

## What is implemented

Electron desktop shell with an isolated React renderer, narrow validated main-frame IPC, native folder/binary selection, local SQLite projects/task journals/checkpoints, bounded content snapshots and file comparisons, actual package-script checks, direct Vite and tutorial preview processes, exact-revision review gates, and a copied interactive tutorial. Windows uses a separate native exec compatibility adapter with bounded independent file-editing runs, strict JSONL completion evidence, configuration checks and confirmed cancellation. The supplied SDK adapter remains available on supported non-Windows hosts with its original strict sandbox gate.

## Proof boundaries and remaining limitations

- Official native Muse **1.4.13-R6996.1** is installed. The user ran Meta's official installer after automatic approval review blocked the agent's launcher download, then completed the official sandbox setup/UAC and browser sign-in. The user reported the CLI's successful model-access verification; MuseBench did not read or copy credentials.
- The real native binary reports host **1.4.13**, stable schema **1**, fingerprint `sha256:7fddaf646dbc317e5fcac0785e135eb04df14fbb0db1863089dfd6da21730e5b`, matching SDK **1.4.13**. `sandbox windows check` reports ready with all readiness flags true. However, the same binary's `serve` initialization reports **sandbox unavailable**, without a reason. The app closes the host before any session or model request. Evidence and the native executable hash are in `artifacts/muse-install/verification.json`.
- The discrepancy reproduces outside Electron, with the echo provider, with restricted network settings, and with additional OS environment variables. Its symptom matches open [Meta SDK issue #107](https://github.com/meta-models/muse-code-sdk/issues/107); the exact native implementation cause remains unconfirmed. Sandbox enforcement was not disabled. The documented `muse exec --json` path provides a separate native entry point; MuseBench now uses it on Windows with Ask me and without sandbox-disabling flags.
- The exec compatibility connection works in the actual Electron application. Connection-only reports say **connection_ready**, `endToEndVerified: false`, and `modelCallAttempted: false`. They check version, sandbox readiness, absent managed configuration, fixed Ask me arguments, and inert echo protocol completion. The separate direct model attempt reports **HTTP 402: Billing verification failed** in `artifacts/workaround-probe/2026-10-25T22-22-01-555Z/report.json`; no file edit occurred. The user then resolved billing. A subsequent full packaged run passed: exact model-generated edit and inventory, authoritative completion with exit zero, both preview filter states, three project tests, checkpoint acceptance and restart persistence. The separate file-tool probe passed: native `write_file` returned “absolute path is outside the workspace” for the exact sibling sentinel path, the sentinel hash stayed unchanged, and the inside edit succeeded. Outside reads were allowed. The first observer missed `edit_facts.path`; saved native records were independently replayed to correct the report without another model call, and the original report was retained. See `artifacts/sandbox-probe/run-1nLnY2/report.json`. This mode does not exercise OS shell confinement because agent shell tools are disabled. See `LIVE-WORKFLOW.md`.
- In the non-Windows SDK adapter, one documented experimental capability is negotiated for permission inspection. Hosts without that capability and a verified sandboxed Ask me profile are refused. Muse sign-in stays with the official native runtime; no user credentials were collected or copied.
- Windows exec mode withholds agent shell/web/reminder/input tools and disables hooks per run. It rejects configured external tools, saved workspace trust and managed configuration that cannot be safely excluded. Readiness and fixed arguments are not dynamic MSP permission evidence or proof of OS-level confinement. Unsupported interactive approval stops the run without granting permission; there is no automatic retry.
- The tutorial's plan/edit are deterministic and labeled. Its files, preview, check subprocess, revision hashes, and SQLite checkpoint are real.
- The app supports one active task/preview/check at a time. Tasks are journaled in SQLite; the UI shows current work and checkpoint history, not a full archived-task browser.
- Project opening currently requires package.json. Preview recipes support direct Vite development and the included tutorial. Static build previews are refused without matching build evidence. User input dialogs, automatic reconnection/replay, model selection, extensions, Git operations and deployment are outside this release.
- Snapshot scope excludes generated directories, credential filenames and unsupported links. It is bounded to 4,000 files, 2 MiB per file, 24 MiB total. It is not a backup and excluded files are not covered by the revision hash.
- Check success means the selected visible npm script exited zero. Implicit lifecycle scripts are suppressed; checks time out after two minutes. Manual preview inspection and acceptance do not prove every acceptance criterion automatically.
- Source revisions are checked on refresh/focus, periodic UI refresh and evidence actions. Observed edits invalidate running checks even when later reverted. This is not an OS filesystem transaction capable of detecting every transient external edit between observations.
- A checkpoint is a local acceptance record and retained file manifest, not a Git commit, deployment or restore command. No push, remote repository, subscription purchase, outreach or other-project modification occurred. The initial model request was rejected by Meta billing; subsequent authorized workflow requests succeeded after the user resolved it. Official CLI installation, its Windows sandbox setup, and user-managed sign-in are machine-level changes authorized for this integration test.
- Windows package is unsigned. A user must keep its companion files beside the executable. The machine already had Node/npm for project commands; those tools are not bundled as a standalone development toolchain.
