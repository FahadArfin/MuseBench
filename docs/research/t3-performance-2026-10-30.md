# T3 Code responsiveness and reliability comparison

Read-only source study, 2026-10-30. MuseBench baseline: `0f83414eb387e1a9120c38aeb435d5bba2fb102f`. T3 Code: `pingdotgg/t3code` at `e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa`; both revisions were checked locally. Source inspection only: no upstream code execution, dependency installation, model requests, personal-session benchmarks, or product changes. Upstream documentation and repository instructions were treated as source material, not operating instructions.

The useful transfer is a small set of interface mechanisms. Keep Muse as the runtime and preserve existing action admission, durable drafts, ordering, context limits, and mobile pairing. Nothing below claims faster inference, lower provider latency, or better model quality.

## Recommendations in priority order

| Priority | Concrete gap | User benefit | Smallest useful change | Evidence strength |
|---|---|---|---|---|
| 1 | Reading position and follow intent are lost on chat switches | Return to the paragraph being read; streaming does not pull a small upward gesture back down | Task-keyed position/follow hook around the existing transcript element | Direct current behavior in MuseBench; T3 implements and tests the relevant state transitions |
| 2 | Existing find resets selection on transcript mutations and covers rendered content only | Keep the chosen occurrence in place as a reply streams; clarify and optionally extend history coverage | Preserve stable message/occurrence identity in existing ChatFind; reuse durable history for out-of-window hits | Direct reset in current code; no duplicate Find UI needed |
| 3 | Composer typing and each accepted snapshot enter the outer App/transcript render path | Keep typing and controls responsive during a busy transcript | Measure first, then add a stable transcript/row boundary; escalate only if the fixture demonstrates a material cost | Render path is source-proven; size of real latency improvement is unmeasured |

### 1. Preserve each chat's reading position and make live following respond to user intent

**MuseBench evidence.** [App.tsx:276](../../src/ui/App.tsx:276) resets `scrolledUp` on every `task.id` change. The adjacent effect scrolls to the end whenever `task.messages`, shell results, runtime state, or that boolean changes. [App.tsx:494](../../src/ui/App.tsx:494) decides whether the user is reading older content solely from a 100-pixel end-distance band. A small upward gesture inside that band remains eligible for auto-follow. The preload receives cloned snapshots and the controller returns a structured clone, so array identity is not a precise signal that transcript content grew: [preload.cjs:5](../../electron/preload.cjs:5), [controller/index.mjs:295](../../src/controller/index.mjs:295). The prompt minimap already exists; its instant jumps and keyboard support must remain intact: [prompt-timeline.mjs:49](../../src/shared/prompt-timeline.mjs:49).

**T3 mechanism.** [timelineScrollAnchoring.ts:94](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/timelineScrollAnchoring.ts#L94) stores row identity, offset within the row, absolute fallback offset, and `atEnd`, with an LRU bound of 100 thread positions. [useTimelinePositionRestore.ts:67](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/useTimelinePositionRestore.ts#L67) restores the saved row and cancels an in-progress restore when the viewport receives navigation. Its settle loop is bounded to 60 frames, so a reply whose end keeps growing cannot run correction forever. [useTimelineFollow.ts:184](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/useTimelineFollow.ts#L184) keeps follow state scoped to a visit, prevents late work from another visit changing the current one, and makes upward input release following immediately when content can scroll. This is stronger than only comparing end distance.

**Minimal Muse implementation.** Extract a transcript hook keyed by project/task ID. Record the first visible `turn-*` row and its offset relative to the scroll container, plus end-follow intent and an absolute fallback. Keep a bounded in-memory map; no new persistence is required. Restore in layout timing once the destination transcript exists, fall back safely if the retained 150-message window no longer contains the row, and cancel pending correction when the user navigates. An explicit Jump to latest re-arms following. Wheel/PageUp/touch/scrollbar intent can release it without waiting for a 100-pixel displacement. Use content growth/size observation rather than any cloned-array change as the scroll trigger. Maintain separate ownership for prompt-minimap jumps, find navigation, and restoration so they cannot fight. The plain DOM list does not require T3's LegendList settle machinery or a virtualization dependency.

**Meaningful verification.** A deterministic browser fixture should read the middle of chat A, switch A→B→A, and verify the same message remains at the same relative position after layout. Repeat with changed reply height, resize, a missing old row, and a late image layout. While a synthetic reply streams at the bottom, issue a short upward gesture; later chunks must not pull the reader down. Jump to latest must resume following. Rapid A→B switches must cancel A's callbacks; keyboard/minimap jumps and reduced motion must work. Track restoration error in pixels and visible jump frames; choose a small explicit tolerance after font/layout stabilization, rather than treating test completion as proof of a smooth experience. T3's [timelineViewport.test.ts:46](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/timelineViewport.test.ts#L46) tests follow release/re-arm transitions; [useTimelinePositionRestore.test.ts:5](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/useTimelinePositionRestore.test.ts#L5) tests that a constantly moving end still settles within a bound. Those files were read, not executed.

### 2. Make existing Find stable during streaming; extend its scope deliberately

**MuseBench already has this UI.** [ChatFind.tsx:21](../../src/ui/ChatFind.tsx:21) implements Ctrl+F, previous/next occurrence, counts, escaped literal matching across inline DOM text nodes, and CSS Highlight ranges without changing React's message DOM. [App.tsx:487](../../src/ui/App.tsx:487) mounts it. Adding another Find bar or presenting next/previous as missing would duplicate shipped capability.

**The exact gap.** [ChatFind.tsx:32](../../src/ui/ChatFind.tsx:32) runs `setRanges(findRanges(container,query));setIndex(0)` on every observed transcript mutation, scheduled through an animation frame. [ChatFind.tsx:39](../../src/ui/ChatFind.tsx:39) then scrolls the active range into the center of the transcript whenever the range array changes. Consequently, after selecting a later match, the next streamed DOM update resets selection to the first occurrence and requests a scroll to it. This is a source-proven correctness issue even if the total scan cost is small. It can also compete with App's end-follow effect. Current matching scans rendered messages only, so “No matches in this chat” can be misleading for older saved messages outside the 150-message window or text beyond the renderer's 16,000-character display cap.

**T3 mechanism.** [useThreadFind.ts:54](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/useThreadFind.ts#L54) identifies selection by entry ID, run ID, and occurrence, rebases it when live results refresh, and keeps the timeline navigation identity stable across count-only updates. Refresh is coalesced with a 300-ms timer rather than treating every mutation as new navigation. [useThreadFindNavigation.ts:34](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/useThreadFindNavigation.ts#L34) rechecks selection/list identity in async continuations and tracks whether a match was already revealed, avoiding repeat jumps merely because data changed. Server [ThreadFind.ts:235](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ThreadFind.ts#L235) caches parsed text, invalidates scan results by revision, yields while counting, and can return progressive results. Only the selection and refresh ownership patterns are needed for the immediate Muse fix.

**Minimal Muse implementation.** Keep ChatFind and its controls. Represent the selected match by stable message ID plus occurrence/character offset. Refresh ranges as content changes, preserving that selection if it still exists; clamp or choose a documented neighbor only if the selected occurrence disappears. Assign a navigation generation only when the user changes query, presses next/previous, or explicitly chooses a result. Rebuild highlights on content refresh without recentering an already revealed match. Make find navigation release transcript end-follow through the same scroll ownership used in recommendation 1. Coalesce live refresh work if profiling warrants it, and avoid a full scan when a mutation cannot affect message text. Preserve cross-node matching and CSS Highlights.

**Scope follow-on, not a second Find UI.** Existing global library reads already use a debounced, one-active/one-latest stale-safe queue: [ChatLibrary.tsx:51](../../src/ui/ChatLibrary.tsx:51), [useLatestRead.ts:9](../../src/ui/useLatestRead.ts:9), [latest-read.mjs:2](../../src/shared/latest-read.mjs:2). [chat-history.mjs:67](../../src/controller/chat-history.mjs:67) returns one newest matching message per task, while [HistoryMessages.tsx:4](../../src/ui/HistoryMessages.tsx:4) pages older messages and 12,000-character excerpts. Label the present Ctrl+F scope as loaded conversation content immediately. If the product wants complete app-received-history find, extend the existing Find with an explicit saved-history scope backed by a task-scoped read API over `chat_history`, stable message/occurrence cursors, and bounded result excerpts. Reuse the token index and exact-substring verification; retain partial-word and punctuation behavior. Out-of-window hits can open the existing saved-history reader rather than loading unlimited rows into the live transcript. Exact total counts can remain optional if they would delay next-match navigation. Preserve legacy/imported coverage labels and do not imply native tool transcripts were captured.

**Meaningful verification.** With Find open on occurrence 3 of a fixed synthetic transcript, stream an unrelated later answer and verify the active occurrence remains 3, its highlight updates correctly, and the viewport does not repeatedly jump. Append text with earlier/later matches, delete the selected occurrence, change query/task, and verify explicit behavior without stale selection. Test matching across inline formatting, code, emoji, punctuation, and next/previous wrap. Test find versus auto-follow/minimap/navigation ownership and a selected range whose surrounding markdown remounts. For any history-scope extension, cover messages older than 150, bodies beyond the first displayed excerpt, and retained-only legacy coverage. T3's [threadFindHighlights.browser.test.tsx:12](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/threadFindHighlights.browser.test.tsx#L12) covers cross-token spans, and [threadFindStore.test.ts:28](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/threadFindStore.test.ts#L28) tests viewport/result handoff. Measure scan time and input/next-match latency using fixed local fixtures, not personal provider sessions. No new backend, search engine, or paid model request is required.
### 3. Contain transcript rendering before considering transport or state-library replacement

**MuseBench evidence and existing protection.** [App.tsx:188](../../src/ui/App.tsx:188) owns `useCodeDraft`; each keystroke updates that hook's React state and re-enters App. [App.tsx:197](../../src/ui/App.tsx:197) also replaces outer state for every accepted canonical snapshot, and [App.tsx:464](../../src/ui/App.tsx:464) filters/maps the transcript in that component. This proves a broad render/reconciliation path, not that it causes noticeable lag on the user's machine. Settled markdown is already memoized by its text prop at [App.tsx:84](../../src/ui/App.tsx:84); [ResponseActions.tsx:6](../../src/ui/ResponseActions.tsx:6) is memoized; [ChatSidebar.tsx:14](../../src/ui/ChatSidebar.tsx:14) stabilizes handlers and compares semantic sidebar data across cloned snapshots. Therefore claiming that all settled markdown or the whole sidebar rerenders per token would be incorrect.

**T3 mechanism.** [threadDetail.ts:242](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/client-runtime/src/state/threadDetail.ts#L242) publishes a stable structural projection through text-only changes; [threadDetail.ts:290](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/client-runtime/src/state/threadDetail.ts#L290) keeps the timeline's item array quiet while individual assistant rows subscribe to their own text. [ThreadTimeline.tsx:18](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/ThreadTimeline.tsx#L18) separates live text from outer ChatView, and [useTimelineRows.ts:39](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/useTimelineRows.ts#L39) derives rows incrementally. Tests [threadDetail.test.ts:150](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/client-runtime/src/state/threadDetail.test.ts#L150) check stable identity through text deltas while status changes still propagate. The benefit is separating update frequency by consumer.

**Minimal Muse implementation and gate.** First create a synthetic render/input measurement fixture. Then extract a memoized `CodeTranscript` and stable row components with narrowly specified data and stable committed callbacks, following the sidebar's existing pattern. Composer text must not be a transcript prop. Preserve the existing markdown memoization; avoid deep comparing a full AppState or stringifying every message each render. Normalize/reconcile only the small renderer view if cloned snapshots otherwise defeat row identity. If measurements still show meaningful outer-render cost during stream updates, a renderer-only selector store can expose quiet structure plus message text by ID while ingesting the existing ordered envelopes. That is a second step, conditional on evidence; do not begin with a wholesale atom/RPC migration. New rows, terminal status, errors, approvals, tool activity, and task switches must still update immediately. Leave action promises and CS04 acknowledgements intact; a preload acknowledgement currently means snapshot delivery to consumers, not React paint completion.

**Meaningful verification.** T3's [renderScenarios.renders.tsx:1](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/test/renderScenarios.renders.tsx#L1) uses fixed fixtures for mount, streaming, switching, and typing, counts commits/component renders, warms lazy assets, and explicitly notes it mounts composed components rather than a connected ChatView. Adopt the measurement discipline, not its result as evidence for MuseBench. Measure current and changed Muse fixtures with 0/50/150 retained messages, settled markdown, code blocks, tool activity, simultaneous typing, and a fixed burst of synthetic snapshots. Record transcript row renders, total commit time, input-to-next-paint p50/p95, long tasks, and pending delivery depth. A structural goal is zero settled-row renders caused only by composer typing; stream-only text should update the owning row and required scroll/status consumers. Require complete final text, unbroken focus/selection, immediate terminal state, and no stale action closure after rapid navigation. Report timings with hardware/build mode and repeatable workload. Do not promise an arbitrary percent improvement before collecting a baseline.

## Already covered; do not re-propose

- **Bounded renderer delivery and ordering:** [renderer-state-publisher.mjs:4](../../electron/renderer-state-publisher.mjs:4) already allows one in-flight plus one latest pending state, uses generation/revision ordering, suspends at two seconds, and resumes with a fresh canonical read after late acknowledgement. [preload.cjs:5](../../electron/preload.cjs:5) rejects stale envelopes while keeping exact action results independent. [main.mjs:167](../../electron/main.mjs:167) observes notifications independently of publisher backpressure. Existing publisher/preload tests cover these contracts. CS04 is not an outstanding opportunity.
- **Native navigation proof:** CS03 already separates semantic navigation from optional visual settling. Do not replace that with an unbounded render wait or conflate a paint with action admission.
- **Durable drafts:** [controller/index.mjs:491](../../src/controller/index.mjs:491) explicitly queues saves without building/publishing snapshots or flushing runtime progress; [code-drafts.mjs:13](../../src/controller/code-drafts.mjs:13) uses an independent authoritative table. The renderer still saves each edit; adding a debounce could weaken acknowledged-edit durability and is not justified by this comparison.
- **History, search and event batching:** history has indexed candidates, full captured bodies independent of the bounded display window, bounded pages/excerpts, and coverage labels. Controller runtime presentation already coalesces replaceable updates on a 40-ms timer at [controller/index.mjs:305](../../src/controller/index.mjs:305). Search uses a one-active/one-latest read queue. These are existing strengths, not T3-only ideas.
- **Mobile:** MuseBench already has desktop-paired Code. A new mobile or backend replacement project is outside this gap analysis.

## Delivery, cache, routing, and deferred candidates

T3 has a real server-oriented delivery design: [ThreadStream.ts:19](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ThreadStream.ts#L19) bounds reconnect replay to 128 events and 1 MiB raw/encoded payload checks, otherwise sends a current bounded snapshot with history cursor. [ThreadStream.test.ts:114](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ThreadStream.test.ts#L114) tests replay/snapshot fallback and oversized raw payload rejection. Its Electron backend supervisor [DesktopBackendManager.ts:545](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/desktop/src/backend/DesktopBackendManager.ts#L545) drains child output and retries readiness probes while a cold backend remains alive. These address T3's separate HTTP server/WSL environment topology. MuseBench's local controller and ordered Electron publisher have different ownership. No evidence here supports adding a server or port, replacing Muse, changing authentication, or claiming websocket deltas are intrinsically faster.

T3 intentionally keeps ChatView mounted across draft promotion: [thread route](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/routes/_chat.%24environmentId.%24threadId.tsx#L3) is an empty child of the owning chat layout; [router.ts:9](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/router.ts#L9) enables intent preloading. [ChatView.logic.ts:339](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/ChatView.logic.ts#L339) remembers 16 ready timelines, and ThreadTimeline only falls back to the cache for the matching active thread; ephemeral preview URLs are excluded. MuseBench already retains outer App and has locally available chat history, so route-library or cache-stack replacement is not an established gap. Only add lazy panel loading or a bounded renderer cache if cold-open/switch profiling shows an actual blank interval or bundle cost. Never display the previous chat as destination placeholder content.

Full list virtualization is also deferred. T3's LegendList supports larger, paged transcripts; MuseBench currently retains at most 150 messages. Virtualization could break DOM prompt navigation, selection, find highlights, source anchors, and accessibility while adding measurement complexity. Establish DOM/layout cost with a representative 150-message fixture first. If it is material, trial virtualization behind that fixture, preserve the history API, and verify those interactions before considering it a win.

A narrower measurement candidate is the prompt minimap: [prompt-timeline.mjs:56](../../src/shared/prompt-timeline.mjs:56) rescans visible prompt/answer DOM and reads rendered text on a throttled 100-ms mutation refresh. T3 derives items from row data and only builds the active tooltip preview, bounding markdown input to 1,500 characters: [timelineMinimapItems.ts:16](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/timelineMinimapItems.ts#L16), [TimelineMinimap.tsx:68](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/web/src/components/chat/TimelineMinimap.tsx#L68). If profiling attributes meaningful layout/text cost to this observer, cache preview text by stable row/text identity and update only affected excerpts or compute the tooltip lazily. Preserve the shared self-contained implementation's guarded remote-page use; a Code-only optimization must not silently change other products. It is a candidate, not a demonstrated bottleneck.

## What this report establishes

There is a missing continuity affordance (per-chat reading-position restoration) and a concrete stability gap in the existing Find (streaming mutations reset its selected occurrence). Full durable-history search scope is an optional extension to that existing Find, not a missing Find interface. Rendering has a source-proven broad update path with existing memoization protections; its practical latency benefit needs a fixed-fixture baseline before implementation expands. No throughput benchmark was run, no upstream test was executed, and no product performance claim follows from comparing source size, frameworks, or protocol names.
