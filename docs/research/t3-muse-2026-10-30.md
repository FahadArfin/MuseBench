# T3 Code: native Muse and context research

Read-only comparison on 2026-10-30. MuseBench baseline `0f83414eb387e1a9120c38aeb435d5bba2fb102f`; T3 Code source `pingdotgg/t3code@e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa`. All upstream links below are pinned to that commit. No dependency installation, tests, executable/host probe, provider/model request, account change, or credential-content read was performed. Recommendations are source-backed opportunities, not verified native acceptance.

**Recommended immediate selection:** implement only a bounded source-linked quote draft from a saved local chat message. Reuse the current editable-draft path and permission boundary. Include source task/message identity, exact selected text or a bounded full-message quote, source hash and a readable attribution; never send automatically. This is the smallest practical slice of opportunity 2 below. Context budgeting and new native recovery behavior are follow-up research, not part of this selection. Keep the existing manual ContextHandoff's safe 8,000/16,000-character limits and explicit overflow errors unchanged.

## Architecture conclusion

Keep Muse. T3 has a genuine `@muse-code/sdk` MSP adapter; its Muse workflows are not dependent on converting a Claude or Codex account into Muse access. T3's README says to install and authenticate each selected provider separately ([README lines 5–22](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/README.md#L5-L22)). Its Muse guide adds a disabled-by-default Muse instance, host-local `muse login`, host-local model catalog, optional instance-specific `META_API_KEY`, and shared saved login among instances on the same host ([Muse guide lines 3–44](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/docs/user/providers-muse.md#L3-L44)). This is individual provider authentication and billing, not one universal subscription. T3 explicitly says status discovery cannot establish login and cached models can be returned while logged out ([status.ts lines 149–171](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/status.ts#L149-L171)).

T3's adapter declares native permission enforcement, interrupt/active steer/queue, native identities, live-only approval callbacks, system/developer context unsupported, attributed synthetic-user handoffs supported, no native fork or rewind, and no child wait/close/fork interfaces ([adapter.ts lines 99–186](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/adapter.ts#L99-L186)). It actually starts/resumes native sessions, checks selected instance ownership, subscribes to notifications, sets the selected model, sends native images, and supplies session MCP connections. It is therefore useful evidence for native Muse design; it is not authority for transplanting another provider's protocols.

Important version difference: T3's Muse package pins SDK `1.4.6` ([package.json](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/package.json#L37-L43)); MuseBench's `reference/patchlight/adapter/compatibility.mjs:1` pins candidate SDK/host `1.4.14`, schema 1, fingerprint `sha256:c94c3d1f2f51e6424074b9ec43eac3eedcf532d3dcd77351ec1383a87d3049c6`. The installed dependency manifest also says `1.4.14`. The latter are eligibility/source facts, not evidence that the currently installed host is available or qualified. Historical MuseBench 1.4.13 diagnosis must not be presented as current host status.

## 1. Capacity-aware, auditable continuation context

**Value:** large chats, selected files and images should have an explicit continuation plan before a native turn fails for capacity. Give the user a reviewable way to continue in a fresh Muse session while keeping the complete local chat searchable.

**T3 evidence:** [handoffBudget.ts lines 22–125](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-core/src/server/handoffBudget.ts#L22-L125) ties telemetry to accepted native identity, subtracts current input/attachments/existing context, respects known windows, and reserves room for instructions/tools/work. [Lines 127–274](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-core/src/server/handoffBudget.ts#L127-L274) retain intact attributed items, prioritize recent user/assistant and initial user requests, include failed/interrupted status, and identify omissions with an exact paginated thread-reading route. These are conservative estimates (one UTF-8 byte charged per token; image allowances), not a tokenizer or context guarantee. [ProviderTurnStartService.ts lines 1116–1201](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ProviderTurnStartService.ts#L1116-L1201) checks whether resumed/fresh sessions fit, refuses replacement while background work remains, and records replacement reason. [ContextHandoffDelivery.ts](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ContextHandoffDelivery.ts#L15-L100) tracks delivery before injection and treats ambiguous delivery distinctly.

**Real MuseBench gap:** `src/shared/chat-context.mjs:1–54` has a fixed 64,000-character context ceiling and `ceil(characters/4)` estimate. It keeps a suffix of the nearest message when an intact message will not fit. `src/shared/context-handoff.mjs:1–5` has a separate manual 8,000-character message/16,000-character packaged handoff limit. Native telemetry already exists in `src/shared/native-context-usage.mjs`, selected model `contextLimit` already exists in `src/shared/models.mjs`, and `src/controller/recent-context.mjs` already stages hash-bound post-compaction excerpts. These pieces are not connected to a capacity-aware handoff planner. `src/controller/index.mjs:1164–1170` offers explicit continue/fresh recovery, but no budgeted selection receipt or omitted-item retrieval plan.

**Deferred proposed interfaces:** a pure `planContinuation({nativeIdentity, modelSelection, usage, currentRequest, imageMetadata, instructions, sourceRecords, history}) -> {estimatedBudget, selectedItemIds, omittedItemIds, assumptions, inputFits, nativeIdentity, digest}`; a persisted `ContinuationReceipt` with prepared/submitting/admitted/unknown state; a bounded, read-only Muse-facing local-chat history tool with task/item IDs and offsets. Reuse `ContextReceipt` hashes, current queue ownership, exact revision guards and the existing native session identity. Preserve the current request intact and separate from history; explicit estimates must never become “exact remaining tokens.” Launch fresh-session continuation only through the existing user action initially. Do not copy T3's automatic retry/replacement behavior into unknown-input outcomes. These interfaces describe a possible later design, not justification to replace the current safe bounded handoff before native qualification.

**Tests and qualification:** use Unicode and JSON-escaping boundaries; large images plus small known model windows; missing/stale usage; model/window change; exact intact-message selection; no duplicated seeded history; omitted local item retrieval; restart after prepare/admission; digest/source mutation; active child/pending approval/uncertain cleanup blocks replacement. T3 has relevant source tests for byte bounds, native usage, images, delivery persistence and duplicate prevention ([ContextHandoffBudget.test.ts lines 95–250](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ContextHandoffBudget.test.ts#L95-L250), [lines 448–630](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/apps/server/src/orchestration-v2/ContextHandoffBudget.test.ts#L448-L630)). Native qualification later requires the exact supported host/schema, sandbox/permission verification, confirmed cleanup, authorized real-model continuation proving an earlier exact constraint remains usable, and real retrieval of omitted history. Unit selection correctness alone cannot prove model retention.

## 2. Durable typed references for context produced by other panels

**Value:** selected build output, a preview target or a changed-line comment should remain inspectable beside the user's prose after draft saving, queueing, send and restart. A reference can occur exactly where the user discusses it instead of being flattened into an appended prompt string.

**T3 evidence:** [composerContext.ts lines 14–64](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/contracts/src/composerContext.ts#L14-L64) separates durable context IDs from attachment IDs and bounds kinds. [composerContextReferences.ts lines 307–370](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/shared/src/composerContextReferences.ts#L307-L370) projects in-place markers plus a once-per-ID envelope, escapes envelope markup, represents missing records explicitly, and marks duplicate identities unavailable. It is an ordinary text projection compatible with Muse's synthetic user input, not a provider-specific tool API. [Reference tests lines 194–325](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/shared/src/composerContextReferences.test.ts#L194-L325) cover label/identity mismatch, captured terminal range, envelope injection, deduplication and missing/duplicate identities. [Composer reference guide](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/docs/internals/composer-context-references.md#L9-L74) explains draft, transport and rendering separation.

**Real MuseBench gap:** `src/shared/types.ts:127–128` defines a draft as text, selected file references, images and mode; no generalized durable record union or inline occurrence binding. `src/shared/preview-annotations.mjs:44–52` already safely captures a local target but returns flattened text/JSON; `docs/PREVIEW-ANNOTATIONS.md` explicitly says captures are temporary and only added feedback becomes part of the draft. Existing `src/controller/run-changes.mjs` and output artifacts should supply provenance, not be replaced. Existing `src/controller/context-receipts.mjs` covers selected-file/instruction hashes but cannot explain which preview/terminal/comment record a particular phrase references. This is a provenance/editability gap, not “preview annotations are missing.”

**Bounded immediate slice:** a chat message action “Quote in draft” prepares a plain attributed quote from the local stored message. `prepareChatQuote({sourceTaskId,messageId,expectedHash,selection?}) -> {text,source}` should resolve the saved message in the controller, enforce same authorized local project/target ownership, reject unavailable/deleted/changed source and over-limit content, and append through the existing draft action. Do not accept renderer-supplied role/title/body as authoritative. If selection is implemented, require offsets and re-resolve the exact text; otherwise bound the entire saved message and report overflow without silent trimming. The resulting draft stays editable and unsent. A readable source reference can open the originating local chat/message; do not turn it into native message delivery, a peer instruction, or a grant of tool authority. Tests can prove exact source selection, attribution, stale-source rejection, draft preservation and no model call entirely locally. The richer typed-record union below is an expansion path, not required to ship this slice.

**Proposed interfaces:** `ContextRecordV1` with a minimal initial union (`preview-target`, `run-output-excerpt`, `review-range`, existing image/file binding); stable record ID plus owner task/project/source ID, source revision/hash, bounded snapshot and captured range. `projectContextReferences(text, records)` remains pure and returns readable untrusted-data text plus a record receipt. Persist records alongside drafts/messages/queued prompts; keep bytes in existing attachment storage. Let removal/reorder preserve exact reference identity; duplicate/missing/stale records render unresolved and block or require explicit removal rather than guessing. Start with a small local syntax/codec and the existing textarea; Tiptap and a general plugin registry are not prerequisites.

**Tests and qualification:** round trip draft/queue/restart; one payload referenced twice; duplicate IDs; missing attachment; label rename preserving identity; wrong task/project; captured range only; hostile markup; bounded UTF-8 projection; exact sent digest; transcript inspection after send. Native transport acceptance later verifies the actual Muse input contains the projected bounded text once and images use the existing image channel. Model interpretation of a preview comment requires separately authorized real native acceptance. Keep MuseBench's narrower capture privacy rules: do not copy T3's HTML/style fields, remote-page inspection or implicit authority instructions.

## 3. Show native retry/backoff as a nonterminal event

**Value:** distinguish “Muse is waiting for its own retry” from stalled UI, without adding app retries or replaying a command.

**T3 evidence:** [protocol.ts lines 183–190](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/protocol.ts#L183-L190) decodes `turn/retryScheduled`; [adapter.ts lines 1610–1628](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/adapter.ts#L1610-L1628) emits a visible system notice with attempt and reason. Its usage-limit parser is separately able to infer a future reset from quota/usage/refusal text ([usageLimits.ts](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/usageLimits.ts#L5-L42)); that parser should not be copied as an automatic resubmission policy.

**Real MuseBench gap:** `reference/patchlight/adapter/session-adapter.mjs:149–150` recognizes turn start/completion, text/items and context usage, but ignores both retry notifications. `reference/patchlight/adapter/diagnostics.mjs:15–20` only projects bounded terminal failure text. The installed `@muse-code/sdk@1.4.14` declaration `node_modules/@muse-code/sdk/dist/src/msp.d.ts:3394–3420,3448–3475` defines both `turn/modelRetryScheduled` and `turn/retryScheduled` with attempt, next attempt, maximum attempts, retry delay, source range, native identity/cursor and optional machine error kind/status. `dist/src/fold/session-fold.d.ts:262–275` explicitly says these are nonterminal and clear on terminal. This is a directly observed native SDK contract, not guessed compatibility from T3's older SDK.

**Proposed interfaces:** bounded `NativeRetryObservation {sessionId, turnId, viewCursor, sourceRange, kind, attempt, nextAttempt, maxAttempts, retryDelayMs, observedAt, safeReason?, errorKind?, httpStatus?}`; include it in the existing adapter ownership/deduplication gate and runtime status projection; display “Muse retry scheduled · attempt N/M” with locally derived elapsed/delay wording. Persist a bounded audit record if needed, but mark saved observations historical. Clear active retry presentation on terminal, native progress, session change or disconnect. Do not make it an app-owned timer which submits anything.

**Tests and qualification:** foreign-session/turn events ignored; malformed delay/count/source range rejected or unavailable with reason; repeated identical cursor idempotent; conflicting cursor fails closed; terminal clears retry; retry never completes the run, admits queue work, consumes a new command ID or resends input; no absolute retry timestamp invented; no raw secret-bearing machine message displayed. The T3 adapter test file was inspected but no dedicated retry-notice test was found, so do not cite its adapter suite as direct proof of this branch. The installed SDK shape and fake-port tests can establish local projection; a later authorized real transient retry is required to claim actual host delivery/UX. Never force provider failure, exhaust quota, or induce spend just to create that evidence.

## Already covered / do not port

* Durable native sessions, snapshot restore, native fork, side chats, exact-turn steering, compaction, child inspection/control, queued work, context history, receipts, saved instruction snapshot replacement, retention safeguards and approved on-demand tools already exist. Audit actual current code before calling historical roadmap bullets gaps. Relevant current paths include `src/runtime/index.mjs`, `src/runtime/session-fork.mjs`, `src/runtime/children.mjs`, `src/runtime/child-inspection.mjs`, `src/controller/recent-context.mjs`, `src/shared/chat-context.mjs`, `src/controller/context-receipts.mjs`; contract tests include `test/native-session-fork.test.mjs`, `test/session-durability.test.mjs`, `test/native-context-usage.test.mjs`, `test/context-receipts.test.mjs`, `test/recent-context-controller.test.mjs` and the adapter tests. These tests were read selectively, not run here.
* Do not regress MuseBench's exact fingerprint, sandbox/human reviewer, stale approval, unknown admission and cleanup gates. T3 uses `--trust-workspace` and `--disable-sandbox` for full access ([sdk.ts lines 121–149](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/sdk.ts#L121-L149)); those are not recommendations for changing MuseBench policy. Its persistent approval choices and automatic child-approval handling are not substitutes for MuseBench's digest/revision-bound human approvals.
* Do not copy T3's “Muse cannot fork” limitation: it explicitly falls back to portable context because its adapter rejects completed-turn native cuts ([adapter.ts lines 2354–2382](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/adapter.ts#L2354-L2382)), while MuseBench has its own newer native-fork implementation and receipts. Portable handoff is lossy attributed context, never native tool/approval/reasoning parity.
* Muse-specific context remains synthetic user text: T3 prepends `buildRuntimeInstructions` as a text part in `turn/start`, not an elevated system/developer channel ([adapter.ts lines 2057–2084](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/adapter.ts#L2057-L2084)). Do not copy T3's PR-watching, environment-linking or messaging instructions into MuseBench; they require T3's tools and authorization model. Preserve MuseBench's explicit current instruction snapshot, attributed source data and independent permission boundary.
* Do not add other provider subscriptions, credential imports, third-party model proxying or a universal-subscription claim. T3's stripping inherited `META_API_KEY` is a useful account-boundary observation ([sdk.ts lines 55–65](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/sdk.ts#L55-L65)); MuseBench already curates an OS-only environment in `src/runtime/index.mjs:24–62` and leaves stored credentials to native Muse. Preserve that stronger boundary.
* T3's optional session MCP can let a turn continue without T3 tools ([adapter.ts lines 1818–1830](https://github.com/pingdotgg/t3code/blob/e9a11d4a8261f4c65e385a2b6d2ec3bd6de48caa/packages/provider-muse/src/server/adapter.ts#L1818-L1830)); do not silently weaken required reviewed-tool availability in MuseBench. Its current on-demand discovery and hosted OAuth are already implemented and are not new opportunities here.
* Internal T3 `docs/internals/context-handoffs.md` describes 240-character summaries. The pinned live `ContextHandoffService.ts` also imports the newer intact-history selection/delivery system; 240-character compaction still applies to `makeForkDeltaSummary`, not the complete current provider handoff algorithm. Use implementation and tests together rather than presenting that older prose as the entire context-transfer behavior.

## Evidence boundary

The strongest portable changes are app-owned context selection/receipts and durable typed references; they can be developed and meaningfully tested without changing backend, auth, permissions or invoking a provider. Native retry rendering is a small genuine SDK-supported visibility improvement. None requires multi-provider orchestration. All native claims remain gated on a compatible, available host and observed native events. Existing historical tests, source declarations, T3 fixtures and model catalogs do not establish current credentials, sandbox readiness, live retained context, provider acceptance, or runtime completion.
