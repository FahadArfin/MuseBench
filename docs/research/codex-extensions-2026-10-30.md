## Recommended portable additions

### 1. Explain the origin of each effective MCP setting

**Priority: first.** When a server inherits its executable from personal settings and receives an argument, enabled flag or timeout override from an ancestor project's `.mcp.json`, show which file supplies each effective field and which earlier declaration it overrides. This helps users review why an apparently disabled or familiar server has different behavior in this workspace.

**Upstream evidence:** `codex-rs/config/src/config_layer_source.rs:4-25` models distinct source kinds; `:29-50` defines precedence; `:71-78` keeps versioned materialized layers and a disabled reason. `codex-rs/app-server-protocol/src/protocol/v2/config.rs:392-409` exposes optional layers and a per-key `origins` map. `codex-rs/app-server/src/config_layer.rs:57-63` carries disabled reasons to the API. [Immutable upstream source](https://github.com/openai/codex/blob/a795f961be68383738e56ac396742b3e8451696a/codex-rs/config/src/config_layer_source.rs#L4).

**MuseBench evidence/gap:** `src/runtime/project-mcp.mjs:100-108` already resolves personal settings plus project sources with recursive merge; `:126-128` exposes source paths/digests separately from the effective server list. `src/ui/ProjectMcpReview.tsx:13-24` shows effective definitions and a separate source inventory, without a field-to-source association. `src/shared/customize-types.ts:25-28` has no origins/override chain. This is a presentation/provenance gap, not missing merge or trust enforcement. The existing skill instruction inspector already has `shadowedBy` (`src/shared/customize-types.ts:35`); use the same vocabulary where suitable.

**Bounded design:** extend the existing resolver to record source path + source revision + field name as it merges, including inherited and overridden fields. Display an optional “Why this setting?” disclosure within Project servers. Never return environment/header values; their provenance can say only which source defines a named entry. Preserve current revision, boundary, file-size and symlink rules. Explain only the configuration the existing resolver actually qualifies; do not invent Muse managed-settings precedence or weaken its restricted-mode rejection. No settings write or native connection is needed to inspect the explanation.

**Acceptance:** fixture personal/root/nested-project overrides, recursive map inheritance, arrays/replacements, an explicitly false flag, canonical/legacy personal aliases, unchanged revision stability, source mutation invalidation, and hidden-value leakage checks. Shared browser/Electron rendering at narrow width and keyboard access. Existing project-MCP review/authority tests remain required. A native scripted contract is necessary only if expanding the resolver's currently qualified precedence, which is outside this proposal.

**Dependencies:** existing project MCP snapshot/types/UI; no provider dependency and no native API addition.

### 2. Give on-demand approval cards an exact source/tool summary

**Priority: second.** Keep the native one-time approval request and its complete raw arguments, but add a clearly attributed summary such as “Source: my-tools · Tool: create_issue” for the fixed `discovery_call` gateway. This reduces the effort of reviewing a nested wrapper JSON request.

**Upstream evidence:** `codex-rs/core/src/mcp_tool_call.rs:1711-1722` renders connector-specific approval text or a generic parameter display; `:1734-1756` carries connector identity, tool metadata and displayed parameters into the request. `codex-rs/core/src/mcp_tool_approval_templates.rs:17-30` separates question/elicitation text from structured tool parameters; `:98-120` matches server + connector + tool before applying a template. [Immutable upstream source](https://github.com/openai/codex/blob/a795f961be68383738e56ac396742b3e8451696a/codex-rs/core/src/mcp_tool_call.rs#L1711).

**MuseBench evidence/gap:** `src/ui/permissions.mjs:1-18` currently displays bounded tool name, subject and raw arguments; `src/ui/WorkspacePanels.tsx:147` renders that generic card. Gateway calls necessarily name `mcp__musebench_discovery__discovery_call`, with the actual source/tool nested inside its arguments (`src/runtime/discovery-mcp.mjs:10`). Source/tool outcome attribution is available after completion (`src/shared/workspace-tool-activity.mjs:40-43`), but is not promoted in the approval presentation. Actual native fixture code explicitly asserts the gateway tool identity and exact JSON arguments (`scripts/native-discovery-contract.mjs:91-100`, `scripts/native-discovery-oauth-contract.mjs:97-106`), so this has a concrete contract-testing seam.

**Smallest useful pass:** current native pending contains `kind:'approval'`, `sessionId`, `turnId`, `toolCallId`, `toolName` and string `rawArgs`. The gateway call's JSON arguments are `{sourceId,catalogRevision,tool,arguments}`. Runtime state already retains `toolDiscovery.sources` with `{id,revision,authBindingRevision?}` (`src/runtime/index.mjs:307`); `src/ui/DiscoveryTools.tsx:11` deliberately passes identity only. Show literal source ID and requested tool name when the source matches the current reviewed selection. This needs no endpoint lookup, catalog download or new public projection. A catalog revision in a request is a requested opaque identity, not proof that the schema is current; gateway dispatch still performs that check. `src/runtime/index.mjs:130-140` preserves pending revision and creates one-time decision tokens from native identity. Do not alter that path. Rich source labels/endpoints can be deferred.

**Bounded design:** recognize only the exact app-owned gateway tool name and validated argument shape. Resolve the source ID against the owning connection's reviewed immutable selection, retaining source/config revision and native session/turn/request/revision identity. Show the requested tool name literally; describe server text as untrusted and avoid “safe/read-only” badges. Show a reviewed public endpoint/origin or executable only if already public in that source projection; never expose auth values or substituted private URL paths. Keep original arguments accessible and preserve the existing truncation/incompleteness approval disablement. Stale/unresolvable enrichment falls back to the existing exact raw request; it never substitutes an identity, adds another approval, authorizes a tool or changes a decision token. Native approval and gateway revalidation remain authoritative.

**Acceptance:** unit cases for malformed JSON, wrong wrapper names, unknown source IDs, same-name sources, stale connection/root/session, changed catalog revision and oversized arguments. Verify one-time decision tokens remain unchanged and full raw arguments still gate approval. Shared browser/Electron cases for nested arguments, long names, narrow width and keyboard reading. Extend the bounded native scripted contract to assert source summary + exact raw request for approve/deny; zero added downstream effects on denial, zero extra native turns and zero model inference.

**Dependencies:** a safe, owner-bound public source projection in the approval view; current native `toolName`/`rawArgs` contract. Generic third-party tool templates, persistent permissions and inferred argument semantics are excluded.

### 3. Offer an explicit installed-extension update comparison

**Priority: third; implement after the first two.** Let a user request an update check for a catalog-installed plugin/skill, stage a candidate from its recorded repository/package path, and review old versus proposed commit, file hashes and capability changes before replacement. This addresses maintenance of installed sources rather than adding another discovery catalog.

**Upstream evidence:** `codex-rs/core-plugins/src/manager.rs:519-529` models `local_version` and `installed_version` independently; `:2517-2555` resolves and returns both. `codex-rs/app-server/src/request_processors/plugins/reconcile.rs:33-43` invokes installed-plugin reconciliation; `:45-90` coordinates hook lifecycle changes; `:94-110` reports changed capability categories and failed plugin IDs. [Immutable upstream version source](https://github.com/openai/codex/blob/a795f961be68383738e56ac396742b3e8451696a/codex-rs/core-plugins/src/manager.rs#L519). Codex's authenticated background bundle synchronization is provider-specific and is explicitly not the behavior proposed here. A human-reviewed file/capability diff is an independent MuseBench design inspired by its distinction between installed and available state.

**MuseBench evidence/gap:** `electron/extension-staging.mjs:75-108` already stages bounded public GitHub packages at a resolved commit and `:139-143` returns per-file hashes/source identity. `electron/customize.mjs:174-177` attaches pinned provenance before review and `:195-207` verifies installation and saves `catalog-installations.json`. The installed projection (`src/shared/customize-types.ts:17`) has one version; its command union (`:22`) provides enable/disable/remove/review/install but no explicit update-check/compare operation. `src/ui/CustomizeDialog.tsx:95` shows a new package's files, while `:108` offers installed-plugin enable/disable/remove. Existing re-review on out-of-band changes is not an old/new update comparison.

**Bounded design:** user-triggered check only; no startup polling/download/installation or remote-account synchronization. Begin with catalog-installed entries whose saved source identity and installed digest can both be verified. Stage from the recorded repo/ref/path using existing limits; same-commit result is a no-op. Compare digest inventories and supported capability definitions, not just version strings. An altered/missing installed baseline requires recovery/manual review, not silent adoption. Candidate or current digest changes invalidate the proposal. Preserve the previous package in an app-owned bounded recovery location before replacement; use existing inactive-run mutation guards and CLI semantics. Capability grants must be re-evaluated for the new contents; do not carry MCP/hook authority across a changed digest. Local folder entries can remain manual reinstall until a reliable source baseline exists.

**Acceptance:** mocked GitHub responses for same/new commit, moved path, immutable commit with unchanged declared version, malformed/oversized candidates, file additions/removals, new hook/MCP capabilities, mutation between compare/apply, failed CLI replacement and baseline preservation. Verify old grant invalidation, unrelated plugin stability and no execution during check/compare. Shared UI review/abandon/recovery with zero model/provider calls. Qualify official Muse replace/install semantics with a disposable profile and echo provider before enabling Apply; if CLI cannot preserve or recover the prior package, ship inspect-only comparison first.

**Dependencies:** durable validated installation receipts and candidate/current file inventory; disposable native replacement contract. No promise of automatic third-party format conversion or auto-update trust.

## Delivery boundary

Recommended order: origin explanations, source-attributed approval presentation, then update comparison. All can be developed using synthetic files, mocked public responses and scripted local native contracts without paid inference or personal accounts. Source tests, shared browser/Electron acceptance, native fixture proof, published artifact identity, installation and personal-provider compatibility remain separate gates. This report supplies recommendations, not implementation or runtime acceptance.
